### 0.1 取得口

- ECHONET Lite (UDP 3610) に応答するのは **.202 (JH-RWL8 モニター)** と **.126 (JH-RVB1)** の 2 台だけ（LAN 全ホスト unicast sweep 済み）。監視対象は .202 の `027901` / `027d01` / `05ff01`
- 要求は `0x62` 属性値読出のみ。**`0x65` 設定値読出は 2 台とも未実装**（`0x52` ですら返らない）。`0x61` 設定 / `0x63` 動作要求は送らない（方針）
- 応答は要求の送信元ポートではなく **必ず `192.168.100.199:3610`** に届く → 3610 バインドは必須だが常時バインドは不要（2.5）
- 属性の支持は 3 状態で読む: **ESV 72 = 値あり / ESV 52 = 知っているが配信しない / フレーム無し = 実装自体が無い**

## 2. 取得方法

### 2.1 単発 GET（`/home/takemon/tmp/test/probe`）

```sh
cd /home/takemon/tmp/test/probe
go run . -hosts 192.168.100.202 -get 027901:e0,027d01:d3
go run . -hosts 192.168.100.202 -get 027901:e1 -full   # 応答フレーム全体も hex 出力
```

要求フレーム（14 バイト、EPC 1 個）:

```
10 81  <TID hi> <TID lo>  05 ff 01  <SEOJ 3B>  <DEOJ 3B>  62  01  <EPC>  00
 EHD     TID     SEOJ       DEOJ      ESV  OPC   EPC   PDC
```

- SEOJ はこの機器では `05ff01` で応答が返る（コントローラ経由）。
- 応答の成功 ESV は **`0x72`**。
- 不支持 EPC は **ESV `0x52`** + 空 EDT。
- 存在しない EPC は **無応答**（フレーム自体返らない）。
- EDT は応答の 14 バイト目から始まる。`resp[13]` = PDC（データ長）。

### 2.2 EPC 総当たり（`/home/takemon/tmp/test/epcsweep`）

```sh
cd /home/takemon/tmp/test
go run ./epcsweep -eoj 027901 -lo 0xa0 -hi 0xfe -spacing 1500ms -timeout 1200ms -abort 6
```

**1 件ずつ送信 → 応答待ち → 1.5 秒間隔。** 無応答が `-abort` 件続いたら中止（デバイス保護）。

**`-abort` は「フレームが 1 枚も来ない」件数だけを数える。** ESV 52（不支持）は応答として扱われ、連続カウントはリセットされる。したがって `-abort` が効くのは**デバイスがレート制限で完全に黙った場合**（2.5 のロックアウト）だけで、不支持が並ぶことでは中止しない。支持表を取り切るために `-abort` を上げる必要は実は無い。3.3 の 2 台完走は安全余裕として `-abort 18` で行ったが、`05ff01` で本当に無応答が続いた最長区間は 2 件（`83`→`84`）で、既定の 6 でも完走していた。124 要求を破綻なしで処理できた（1 要求あたり約 2.7 秒）。

### 2.3 multi-EPC GET は使えない

1 フレームに複数 EPC を詰めると（OPC>1）、**どれか 1 つでも不支持だと全体が無応答**になる。属性列挙には使えない。

### 2.4 EPC 0x9f（対応属性一覧）は解析不能

SHARP の返す EDT は PDC `0x11`（17 バイト）で、先頭バイトが `0x01` でも EPC 数でもない。標準形式（`[count][EPC...]` / `[0x01][16 バイトビットマップ]`）のどちらにも当てはまらず、LSB-first / MSB-first 両方で試しても既知の支持属性（0xe0/0xe1）と矛盾した。

```
027901: 1081f0f1 027901 05ff01 72 01 9f 11 276df99d9398808182c301010100030202
027d01: 1081f0f2 027d01 05ff01 72 01 9f 11 34859595e7c4c4e5863715256540030212
05ff01: 1081f0f3 05ff01 05ff01 72 01 9f 11 1401818181808081800101010100030202
```

→ **支持属性の列挙は実測 sweep で行うこと。**

### 2.5 継続ロガー（`/home/takemon/tmp/test/solarlog`）

10 分周期で 10 属性を逐次 GET により取得し、CSV に追記する。**UDP 3610 は 1 周期の測定中だけ掴み、測定が終わったら離す**（2026-10-07 07:02 変更）。

```sh
cd /home/takemon/tmp/test
gofmt -w solarlog/main.go && go build -o bin/solarlog ./solarlog
nohup ./bin/solarlog -interval 10m -cycles 144 -out day.csv > day.log 2>&1 &
```

| フラグ | 既定 | 意味 |
|---|---|---|
| `-host` | 192.168.100.202 | 対象 |
| `-interval` | 10m | 周期（サイクル開始時刻から起算。ドリフトしない） |
| `-spacing` | 1500ms | 属性間の間隔。**7 属性以上なら 1500 ms 以上を崩さない**（レート制限） |
| `-timeout` | 1200ms | 1 要求あたりの応答待ち |
| `-retry` | 2s | **無応答属性の再試行待ち。1 回だけ再送する**（`ESV52` / `PDC` / send 失敗は再試行しない。0 で無効） |
| `-cycles` | 0 (=無制限) | 実行回数 |
| `-out` | solarlog.csv | 出力 CSV（既存があればヘッダーを書かず追記） |
| `-bindwait` | 30s | 3610 が空くまでの待ち上限。超過はその周期をスキップして次の周期を待つ |

CSV 列: `ts, pv_w(027901:e0), pv_kwh(027901:e1), bat_w(027d01:d3), bat_chg(027d01:d8), bat_dis(027d01:d6), bat_e3, bat_e4, bat_cf`

- 取得失敗は `bad=属性名:理由` で理由を出力する（`無応答` / `ESV52` / `PDC` / `send`）。`ok=n/8` が 8 に満ちない周期は CSV の該当セルが空になる
- `ok=0` の周期は 2 分待機してリトライ（レート制限で固まった時の自己回復）
- SIGINT/SIGTERM で安全に抜ける。各行書き込み時に `f.Sync()`
- **応答は要求の送信元ポートではなく必ず UDP 3610 に届く**（2026-10-07 06:58 の tcpdump: ephemeral `199.26173` からの 3 要求すべてに .202 が応答し、応答先はすべて `199.3610`）。したがって 3610 を開けっぱなしにする必要はなく、**測定中だけ bind すればよい**
- 実装: `acquirePort(3610, -bindwait)` を周期開始時に呼び、属性ループ終了で `conn.Close()`。周期待ち (~9 分) は 3610 が空いているので `probe` / `epcsweep` を**ロガーを止めずに**実行できる。掴み中に起動された場合は最大 30 s 待って、その周期を `3610 を取得できず` でスキップ
- 周期は 10 属性 × (`-spacing` + 応答) で最大 ~1 分間 3610 を占有する。単発調査は周期待ちの窓（10 分中 ~9 分）に行う
- **停止検知**: `solarlog-watch.sh` が `pgrep -x solarlog` で稼働を確認し、止まっていれば同じフラグで `nohup` 再起動（稼働中は二重起動しない = 3610 の取り合い回避）。600 s ごとに呼ぶ。この環境は cron デーモンが未稼働なので `while :; do …; sleep 600; done` のループで常駐させ、決定ログは `watch.log`

## 6. 計算で出せるもの / 出せないもの

### 出せる（実測裏取り済み）

1. **瞬時発電量** = `e0`（単位 W、3.4 で確定）
2. **期間発電量** = `e1` の差分 × 0.001 kWh
   例: 5,248,132 − 5,246,203 = 1,929 → **1.929 kWh**
   3.4 の積分検証で裏取り済み。**`e0` を時間積分するより `e1` の差分を取るほうが誤差が少ない**（サンプリング間隔に依存しない、積算値なので取りこぼしがない）。日次・時間単位の集計は `e1` ベースにすべき。
3. **期間放電量** = `d6` の差分 × 0.001 kWh（役割は 3.5 で確定。推定ではなく確定値）
4. **期間充電量** = `d8` の差分 × 0.001 kWh（同上。**効率による推定はもう不要**）
5. **充放電効率** = Δ`d6` / Δ`d8`。累計で **91.8%**（3.5）。期間ごとの効率も同じ差分で出せる
6. **定格利用率** = `e0 / 027901:e8`（`e8` = `157c` = 5,500 W 定格発電電力。例 860/5500 = 15.6%）
7. **蓄電池経由率** = 積算放電 / 積算発電 = 1,729.3 / 5,250.6 = **32.9%**
   積算充電 / 積算発電 = 1,883.5 / 5,250.6 = **35.9%**
   → 発電量の約 1/3 が蓄電池経由で使われ、約 36% が蓄電池に充電されている
8. **充放電の有無と方向** = `d3` の符号（＋充電 / −放電）。`d3` = 0 は待機

### 買電が未知のため部分しか出せない（2026-10-06 14:23 時点の見立て → 20:10 の夜間実測で解消 → 2026-10-11 19:14 に単位確定）

```
負荷 = 発電 + 買電 + 放電 − 充電 − 売電
負荷 [W] = e0 + f3/10 − d3 − f2/10        ← f2/f3 は 0.1 W 単位（3.7）
```

発電(`e0`)・放電/充電(`d3`/`d6`/`d8`) は既知。**売電は `05ff01:f2`**、**買電は `05ff01:f3`**（単位 0.1 W、3.7）。3 オブジェクト (`027901` / `027d01` / `05ff01`) をすべて 0x80〜0xfe まで総当たりした結果、系統連系点に相当する計測点はコントローラのメーカー個別 EPC 以外に無い。分電盤メータリングも B ルートも無い。

`f3` = 瞬時買電電力が成立したので、**買電項を含む負荷の式が閉じた**（2026-10-06 20:10、発電 0 / 放電 940 W / `f3` 生値 480 = 48 W / `f2` = 0 → 負荷 **988 W**）。

| 時間帯 | 負荷 | 根拠 |
|---|---|---|
| 充電中・買電なし（余剰がある） | **`e0 − d3 − f2/10`** | 5.4 結論 A。`f3` = 0 と一致 |

### 近似なら_possible_（前提を明示すれば）

`f2` が売電でなかった場合（5.4 の夜間判別で棄却された場合）のフォールバックがこれ。10 分間隔で 1 日分取れば、各区間を下のいずれかに分類できる。充放電量が `d8`/`d6` の差分で確定できるので、**近似は「どの区間か」の判定にのみ誤差が入る**。

| 区間の状態 | 負荷の式 | 確度 |
|---|---|---|
| 充電中（未满）かつ 充電 ≦ 発電 | **負荷 = 発電 − 充電** | 決定値。ただし「同時買電なし・同時売電なし」の 2 つの制御仮定の上での話 |
| 充電中かつ 充電 > 発電 | 買電 ≧ 充電 − 発電 が強制される | 負荷は**不定**（買電が未知） |
| 充電中だが残量が増えない（満杯の可能性） | 負荷 ≦ 発電 − 充電 | 上界。売電している可能性が開く |
| 放電中 | **負荷 ≧ 発電 + 放電** | 下界。買電が上へ押し上げる余地。同時売電は無い仮定 |
| 待機 かつ 発電 > 0 | 負荷 ≦ 発電 | 上界。売電 0 なら 負荷 = 発電 |
| 夜間（発電 = 0）かつ 放電中 | 負荷 ≧ 放電 | 下界のみ。買電分は不明 |
| 夜間かつ 待機 | 負荷 = 買電 | **取得不能** |

> **以前の表は放電中行の向きが逆だった**（2026-10-05 12:40〜12:50 に day.csv の実データで検証中に発見・是正）。「負荷 = 発電 + 放電 … 上界」と書いていたが、買電 ≥ 0 を足すと負荷は発電 + 放電より**大きく**なるので、発電 + 放電は下界である。逆に充電中行も、充電が発電を超えた瞬間に買電が強制されるため「決定値」は無条件には成り立たない。

「満杯か否か」は `e3`/`e4` の増減で判定するが、**`e3` は 10 分で 15 刻み程度にしか動かず、1 区間不動なだけで満杯とは呼べない**（11:56→12:06 に充電中なのに `e3` が 357 のままだった実例）。実装は「充電中に `e3` 不動が 3 区間以上続いたとき」に限定している。2026-10-06 以降は `e4` が **SOC % そのもの**（3.6・3.2）なので、`e4` を直接見て判定する方が確実。

**状態は `d3` の符号ではなく `cf` で読む（2026-10-06 09:42 確定）:** `cf` = 66 充電中 / 67 放電中 / 68 停止。これが重要なのは、**`d3` = 0 を「平衡点」と「停止」が区別できる**から。3.5 の零点プローブで欲しいのは平衡点（`負荷 ≒ 発電`）だが、13:26 の `d3`=0 は `cf`=67（まだ放電状態）で、夜間の 77 サイクルの `d3`=0 は `cf`=68（完全に停止＝負荷は全量買電）。`d3` の符号だけを見ているとこの 2 つが混ざり、夜間を「負荷 ≒ 0」と誤読することになる。

**瞬時値による補助読み:** 充電中の各サンプルでは `負荷 ≒ e0 − d3` が成り立つ。ただし `d3` は瞬間値で変動が大きく、10 分平均（`e1`/`d8` 差分）とは一致しない。11:46→11:56 区間は差分から 1.38 kW 平均なのに、両端の瞬時値は 1450−270 = 1.18 kW と 2210−1200 = 1.01 kW だった。集計は差分、瞬間の形状だけ `d3` を使う。

**較正点:** `d3` が + から − に転じる瞬間の `e0` が負荷の直接値になる（3.5 で 1.0〜1.26 kW を実測）。この零点を 1 日に何点か持てれば、上の表の「上界」「下界」が実際にどこまで届いているかを検証できる。

## 7. 運用上の制約 — .202 はレート制限で固まる

GET を短時間にまとめると ESV 52 ですら返さず**完全無応答**になり、数十秒〜数分復旧しない。

| 送信パターン | 結果 |
|---|---|
| 40 ms 間隔の逐次、372 要求 | 約 27 件で無応答化 |
| 10 件/chunk + 1.5 s 収集 | 最初の chunk 中（約 10 件）で 3 件しか返らず無応答化 |
| 1 件ずつ + 1.5 s 間隔 | **安定**。95 要求の 027901 全走破、121 応答の 027d01 全走破、1.5 s 間隔 8 属性 × 25 サイクル（175 GET）と × 4 サイクルで**ロックアウト 0 回** |

**solar-monitor のポーリング設計への含意:** 取得属性を 4〜6 個に絞り、ポーリング間隔は 15〜30 秒以上。連続 GET を並列発行しない。復旧を待つ監視は次で検知できる:

```sh
cd /home/takemon/tmp/test
until (go run ./probe -hosts 192.168.100.202 -timeout 800ms -get 027901:e0 2>/dev/null | grep -q 'EDT '); do sleep 20; done
```
